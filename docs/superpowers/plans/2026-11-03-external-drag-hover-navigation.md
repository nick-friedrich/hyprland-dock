# External Drag Hover Navigation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This document requests no delegation or implementation by itself.

**Goal:** While holding a file, image, text selection, or other externally draggable content, hover a Dockrail window or workspace to reveal that destination and continue the original drag into its application.

**Architecture:** Use Qt Quick drag events to identify the hovered destination. A small host-owned coordinator owns the pending hover timer and surface handoff; the existing host-owned `DockWindowActions` remains the sole window/workspace action owner. Dock and sidebar delegates supply stable target identities and never receive, save, or forward the content.

**Tech Stack:** QML/Qt Quick `DropArea`, Quickshell, existing Hyprland dispatch integration, Qt Test, named KVM development sessions. No new dependencies.

**Spec:** The user’s request and the behavior contract below, incorporating their question-tool answers on 2026-11-03: 500 ms default dwell; window previews for multiwindow icons; sidebar browser-tab activation and application-group expansion; stay on the reached workspace after cancellation; enabled by default with on/off and delay controls. With ordinary previews disabled, reveal the app’s workspace and its windows instead of a preview. Each application icon represents its workspace-scoped windows; use that existing workspace identity. The product questions asked so far are settled. This is a plan update, not authorization to implement, deploy, or merge.

## Behavior contract

1. A real external data drag over an eligible target starts a dwell using `dragHoverDelayMs`, default **500 ms**, when `dragHoverNavigationEnabled` is true. Motion within that same stable target does not restart the timer.
2. A workspace target calls `focusWorkspaceInPlace(workspaceIdentity)`. A window target activates that exact live toplevel where it resides; a Dockrail-minimized window is restored to its recorded origin and then focused. Hovering does not pull either destination to another monitor.
3. Activate once per continuous target visit. Moving to a different target starts a fresh dwell; exiting before expiry cancels it. Reprojection after focus must not produce repeated activation of the same target. The fired-target latch is keyed on `(drag session, stable target key)`: a session begins at the first native drag entry and ends only at drop/Escape cancellation or native drag termination — never at delegate reconstruction, surface reprojection, or preview handoff, however long those take. The latch clears only when the session ends, when a different target activates within the same session, or when the pointer genuinely exits the target and the full 200 ms handoff expires without re-entry into that same target. A genuinely new drag session can activate the same target again.
4. A hidden classic dock reveals on an external drag entering its existing reveal strip. It remains open while the drag is on the dock or its window preview. Permit a **200 ms** handoff grace between those surfaces; this grace holds visibility only and never continues an activation timer after target exit.
5. Sidebar coverage includes window rows, workspace rows, collapsed workspace badges, the leading inline workspace badge on the first visible application or window row, exact browser-tab rows, and collapsed application/group rows. Window content and the inline badge must resolve to different targets, with the badge taking precedence in its own rectangle. Precedence is event-order independent: the coordinator grants the badge target priority over its enclosing row target for the same visit (child-target priority), so the badge wins whether its entry arrives before or after the row entry, and a partially clipped badge claims only the part of its rectangle actually visible.
6. Classic coverage includes grouped workspace headers, flat workspace-strip buttons, running application icons, and exact window preview tiles. The classic dock is bottom-only at the inspected head (`classicDockPosition` in `/home/admin/Projects/dockrail/components/DockModel.js:450–455` normalizes legacy vertical values to bottom without rewriting them), so the supported qualification matrix is classic bottom/horizontal plus sidebar expanded and collapsed-rail vertical presentations. Legacy vertical classic settings may be exercised only as defensive normalization tests, never as a supported user-facing configuration.
7. For an icon with one live window, activate that window. For multiple live windows with previews enabled, open the existing preview after the dwell without focusing an arbitrary member; dwelling over a window tile then activates that exact member. Keep the preview alive during content drag, including the gap handoff.
8. With previews disabled, a multiwindow icon reveals the workspace represented by that icon and the windows there, without opening a preview or selecting/cycling a window. In workspace-card layout use the owning card identity; in flat layout use `modelData.localWorkspaceIdentity`. Unresolved workspace identities are ineligible for workspace-only navigation. Do not aggregate an app’s windows across workspaces or choose another workspace using focus history. With zero live windows, do nothing. Reuse the normal compositor workspace presentation, not a new overview or picker.
9. Dwelling over a sidebar browser-tab row focuses its owning browser window in place and activates that exact provider-verified tab. Missing/stale/unavailable provider targets fail closed; do not launch a browser or select a different tab. Dwelling over a collapsed application/group expands it once so its windows become reachable; it must never toggle an already expanded group closed. Reuse session-local fold state and leave the group expanded after exit/cancellation, matching manual expansion; do not persist folds. Launcher-only entries, agents, Widgets, trash, settings, close/mute buttons, and other controls are not navigation targets. Collapsed rail mode already shows individual windows and does not render browser-tab/application-header children; only add navigation to existing visible targets. Existing Widgets retain their own input and drag behavior.
10. Accept drag entry only as necessary to track it; explicitly reject a release on Dockrail navigation targets. The adapter's Qt event contract is: entry remains accepted for tracking so `containsDrag` stays true; `onDropped` sets `drop.accepted = false` explicitly (Qt defaults `DragEvent.accepted` to true on drops, so this override is mandatory) and the source drag terminates normally; no MIME/content predicate is used — empty `DropArea.keys` plus internal-gesture suppression is sufficient. The actual receiving app negotiates the final copy/move/link operation when the user releases there. Do not read `text`, `urls`, HTML, image data, or `getData*` in navigation code.
11. An Escape cancellation, completed/rejected drop, surface destruction, delegate reuse, target removal, screen removal, or presentation-mode change releases the associated drag state. Cancellation leaves the user on the workspace/window/tab reached; do not restore original focus or workspace. Never leave the dock held open or fire a stale timer. Incompatible internal gestures suppress external navigation.
12. Add `dragHoverNavigationEnabled: true` and `dragHoverDelayMs: 500` to the canonical settings. Planner-selected bounds for the delay are integer **100–2000 ms**, with **100 ms** UI steps; these bounds were not separately requested by the user. Both settings belong under **Behavior · Windows**, apply to both presentations, and use existing CLI/Settings host intents and the single writer. Dim/disable the delay control when navigation is off while preserving its saved value. Preserve live reload; disabling immediately clears pending activation and visibility holds, and changing the delay cancels the current dwell so the next target entry uses the new value. Keep the 200 ms visibility handoff internal and independently injectable for tests.

## Review focus

- A browser exposes images as URLs, HTML, image data, or several formats: navigation must not depend on `hasUrls`/`hasText` or fetch content. Task 1 and Task 2.
- Focusing a destination rebuilds or recycles the hovered delegate: no repeated activation, stale-window activation, or held-open dock. Tasks 2–4.
- The pointer crosses the gap into a separate preview surface: the preview remains reachable and the previous activation timer is cancelled immediately. Tasks 2 and 4.
- A modifier changes copy/move negotiation during the drag: it must not trigger Dockrail's Ctrl-click relocation path. Tasks 3–5.
- Destination changes workspace/monitor or disappears during dwell: revalidate its live identity, focus its current location if still valid, and never move it. The existing sidebar `targetIsCurrent` workspace branch (`/home/admin/Projects/dockrail/components/DockSidebarController.qml:664–668`) rejects a workspace whose current monitor differs from the captured monitor — correct for internal relocation, wrong for external navigation. The external path re-resolves the canonical workspace identity and accepts its current monitor. Tasks 2, 3 and 5.
